# WordPress plugin (`wordpress/msp-studio/`)

MSP Studio for WordPress puts the editor in wp-admin and has the artist's own site host the feeds (asked for by a user, Nov 2026: "use WordPress for everything"). It is **built from this repo, not forked**: `npm run build:wp` runs `vite build --mode wordpress` into `wordpress/msp-studio/build/` and `tools/build-wp-plugin.mjs` stamps the version and zips `wordpress/dist/msp-studio-<version>.zip` (both output folders are gitignored). CI runs it plus `php -l`.
- **Shape: a same-origin iframe.** The "MSP Studio" admin page holds a full-height `<iframe>` of `admin-post.php?action=msp_studio_app`, which prints `build/index.html` with a `<base href>` at the bundle folder and `window.MSP_WP` (REST root, `wp_rest` nonce, feed URL prefix, MSP API origin). Not a `<div>` in wp-admin: `App.css` resets `*`, sets `html, body, #root` to 100% height, writes `data-theme` on `<html>` and portals to `<body>`, all of which would break the admin. The frame shares the site's cookies and localStorage, and the iframe's path (`/wp-admin/admin-post.php`) falls through `App.tsx`'s pathname switch to the editor, so `/admin`, `/charts` and `/auth/verify` don't exist in the plugin.
- **Gate on `isWordPress()` (`src/utils/runtimeTarget.ts`), which reads `import.meta.env.MODE`. Never add a Vite `define` constant for it**: the Desktop fork has its own `vite.config.ts`, so a synced file naming a constant that config never defines throws there. For the same reason a root-absolute path to a `public/` file is written `` `${import.meta.env.BASE_URL}name` `` in place, with no new import — `App.tsx` and `InfoModal.tsx` are forked, and an import that merges while its use conflicts is an unused import that fails the fork's build.
- **`/api` calls are redirected once, in `src/main.tsx`**, by `installApiShim()` (`src/wordpress/apiShim.ts`), not at the 40-odd call sites: every file with an `/api` call is already forked on the desktop side, so editing them only adds conflicts. `/api/proxy-feed` goes to the plugin's own `msp/v1/proxy-feed` (WordPress fetches feeds for its logged-in user, so MSP's proxy stays closed — see `_utils/cors.ts`); everything else goes to `MSP_WP.mspApi`, which answers cross-origin. A new `/api` endpoint the editor calls must be added to the public CORS list or it fails only in the plugin.
- **NIP-98 `u` tag:** `adminAuth.ts`/`hostedFeed.ts` build it from `window.location.origin`, which in the plugin is the WordPress site, not the URL the request goes to. Harmless while the server ignores `u` (see `docs/claude/api-security.md`, "Known security follow-ups"); **binding NIP-98 to the URL must also build `u` from the rewritten URL**, or every Nostr-signed hosted write from the plugin breaks.
- **Storage:** one private `msp_feed` post per `podcastGuid` (UUID-validated like `isValidFeedId`), XML in post meta — never `post_content`, which kses rewrites for users without `unfiltered_html`. `update_post_meta` unslashes, so the XML is `wp_slash`ed first or every backslash in a feed is lost. Public address `/msp-feeds/<guid>.xml` (`?msp_feed=<guid>.xml` without pretty permalinks; `MSP_Studio_Public_Feed::base_url()` and `wordPressFeedUrl()` must agree), served with the same `nosniff` + `default-src 'none'; sandbox` invariant as MSP's hosted GET — this is the origin wp-admin runs on. Uninstalling keeps the feeds unless `msp_studio_delete_data_on_uninstall` is set.
- **Save → "Host on this WordPress site"** (WP build only, and its default) PUTs to `msp/v1/feeds/<guid>`, then calls `/api/pubnotify` with the WordPress URL, so the server's submit guard probes the artist's site: a WordPress host behind Cloudflare Bot Fight Mode is refused there and the "Save and submit anyway" latch is the override, as in the PI mode. Import gets "My WordPress Feeds".
- **REST auth** is WordPress's: cookie + `X-WP-Nonce`, and every `msp/v1` route checks `msp_studio_capability()` (`manage_options`, filterable). The proxy route is therefore not an open relay; it mirrors `proxy-feed`'s bargain (`wp_safe_remote_get` per-hop address checks, 20 MB refused not truncated, feed sniff, forced type) and its `{ error, code, status }` shape, so `CODE_MESSAGES` in `xmlParser.ts` apply unchanged.
- **Uploads happen in the editor** (the user's ask: "everything done in one place"). `MediaLibraryButton` ("📁 Upload or choose file", renders nothing outside the plugin) opens `window.parent.wp.media` — the admin page enqueues it (`wp_enqueue_media()` on the MSP Studio hook only) and the frame is same-origin, so the media window opens over the whole admin, Upload tab included, and files land on the artist's own host. Mounted on album/publisher art (`ArtworkFields`, which syncs to the fork), a track's audio/video URL and track art (`Editor.tsx`). **"📁 Add tracks from files"** (`AddTracksFromFiles`, beside "+ Add Track") takes many files at once: `planTracksFromFiles()` (`src/wordpress/bulkTracks.ts`) fills blank tracks first (a new album starts with one), then appends, ordered by the files' tag track numbers when every file has a distinct one, else by pick order. Title, size and length come from the attachment (`title`, `filesizeInBytes`, `meta.length`/`fileLength`); a value WordPress couldn't read is left **empty, never guessed**, so the Feed check and Save gate name the track. Both handlers dispatch synchronously inside the picker callback — no await, so no stale index; don't add async measurement there without dispatching by track id. A single track's button keeps the track's title and clears the old file's size and length. The site's `wp_max_upload_size()` rides on `MSP_WP.maxUploadBytes` and is shown beside the bulk button, because shared hosts often cap uploads below a WAV or FLAC. The fork edits tracks in `TracksSection.tsx`, so the track buttons don't reach the app — they would render nothing there anyway. `class-admin.php` adds `track_number` to the attachment JSON, because WordPress stores it but does not send it. WordPress reads tags only from ID3 (MP3), so a FLAC or M4A file has no track number and takes its title from the file name, and an album with any such file keeps the order it was picked in.
- **Email sign-in in the plugin is "paste the link".** The emailed link always names MSP's own host (`getVerifyOrigin` — don't add a return-URL, that is the phishing hole the hardening closed), so clicking it signs the user in on musicsideproject.com. `EmailLoginModal` in the WordPress build tells them not to click, takes the pasted link, and redeems it with `extractMagicLinkToken()` + `verifyMagicLink()`, storing the session in the WordPress origin.
- **Testing on a real WordPress:** a stand-in hides real behaviour. Five bugs got past the stand-ins and showed up only on WordPress: `add_query_arg()` drops the `=` for an empty value, a plain-permalink site's `rest_url()` already has a query (`?rest_route=/`), `wp.media` does not send `track_number`, a flush on deactivation saves the rule that `init` just added, and the expired-nonce message is "Cookie check failed", so test the `code`. Use WordPress Playground (`npx @wp-playground/cli server --port=9400 --mount=<zip folder>:/zips --blueprint=<file>`, sign in as `admin` / `password`, installing with an `installPlugin` step from `/zips`). It can mislead in three ways. `--php` and `--wp` are ignored with a Blueprint, so set `preferredVersions` in it. `--login` or `"login": true` signs in every visitor, so a logged-out check passes falsely. It filters `http_request_host_is_external` to true, so the proxy reaches private addresses there: judge the guard by calling `wp_http_validate_url()` with that filter removed. Set `MSP_STUDIO_API` to a preview, and stub `pubnotify`, `pisubmit` and `podping` in the browser, or a test publishes for real. Not covered there: a real host's HTTPS, upload limits and bot protection.
